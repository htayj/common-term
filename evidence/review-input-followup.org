* Input mechanism inspection
The window owner serializes command, paste/key/focus and device-response enqueue.
SEND-INPUT copies caller bytes before command publication; SESSION-WRITE copies
again into FIFO-owned storage. Capacity rejection precedes insertion. Successful
calls acknowledge complete enqueue, not delivery. The owner holds INPUT-LOCK
while removing exactly the returned accepted prefix; zero and partial writes
retain the correct offset and suffix. Each scheduler turn writes at most 4096
bytes through PTY-WRITE :TIMEOUT 0. The existing scheduler processes controls
before I/O and sleeps .005 seconds, avoiding a new polling spin.

Responses remain in the engine queue when their entire batch cannot fit. Later
user input is explicitly rejected while that queue is nonempty; further PTY
reads pause until the retained response batch can enter the FIFO. The batch is
ordered by reversing the engine's reverse-chronological queue. Screen and input
lock ordering agrees with status/close; ordinary FIFO write/flush does not acquire
the screen mutex in the inverse order. Quiesce joins the owner without clearing
input. Close stops the owner, closes/reaps the PTY, then clears/counts queued and
engine-owned bytes and signals INPUT-CANCELLED after marking the host closed.
Saver detach replaces the added input mutex without acquiring its inherited copy.

* New MEDIUM: PTY read-loop mutex reacquisition starves close
Locations: =src/pty/posix.lisp:50-71= and =src/pty/process.lisp:88-102=.
PTY-READ releases the transport mutex after each .05-second poll and calls
THREAD-YIELD, but can immediately reacquire it repeatedly ahead of CLOSE-PTY.
CLOSE-PTY cannot publish close intent until it obtains that same mutex. A long
read deadline therefore defeats the claimed short-slice close bound.

The existing PTY suite's CLOSE-BOUNDED assertion failed twice independently:
=unit.log= and =pty-retry.log=. A subsequent identical unit dispatcher passed.
A separate 12-iteration real PTY probe confirmed this is not just assertion
printing overhead: open a PTY with no child, start PTY-READ :TIMEOUT 30 in another
thread, sleep .1, time CLOSE-PTY plus joining the reader, without printing inside
the timed region. Observed seconds:
#+begin_example
4.565932 .952986 .001 1.30398 5.419919 10.740839
2.908956 2.113969 .65499 .001 1.453978 .051
#+end_example
Seven of twelve exceed the existing 1-second assertion. All readers eventually
returned :EOF; there is no child termination delay in this probe. Full input and
output are retained in execution =841ba2f3-3262-407f-a1ff-d92c357fdc5d=,
=extra-retry.log=. The observed delay is established; unfair repeated mutex
reacquisition is the source-supported explanation, not an instrumented scheduler
trace. Parent notified promptly for a separate repair. No repair attempted here.
A fix should establish a reliable close/control handoff, preserve fd-reuse safety,
and independently rerun repeated long-read/close plus the PTY suite.
