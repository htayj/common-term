* HIGH: compositor keymap FD can cause native SIGBUS
Location: src/display/xkb.lisp:34-48.
The advertised keymap size is bounded but the received FD's accessible backing bytes are not checked. mmap succeeds beyond EOF; libxkbcommon then accesses invalid pages. A malformed or concurrently truncated keymap can signal a native bus error in the live Lisp heap rather than a typed transport failure.

Disposable reproduction, exit 1 with SBCL Signal 7 CORRUPTION WARNING and bus error:
#+begin_src sh
scripts/sbcl --non-interactive --eval '(require :asdf)' --load scripts/bootstrap.lisp --eval '(asdf:load-system "lispterm/display-wayland")' --eval '(let ((fd (lispterm.display.wayland::%memfd-create "review-empty-keymap" 1))) (lispterm.display.wayland::xkb-from-fd fd 8193))'
#+end_src

Recommended repair: read the bounded expected bytes into owned memory, reject short reads/invalid terminator, then parse. fstat alone does not prevent concurrent truncation.

* MEDIUM: malformed keymap event loses ancillary FD ownership
Location: src/display/xkb.lisp:85-86.
The FD is popped before either payload word is validated. If payload parsing fails, neither xkb-from-fd's unwind-protect nor wire-close owns this FD.
Reproduction in disposable loaded Wayland system: create memfd, put it alone in %make-wire :fds, create make-wayland-state :wire wire, call keyboard-event state 0 with an empty octet vector under handler-case, then wire-close. Observed INVALID-ARRAY-INDEX-ERROR and sb-posix:fcntl fd sb-posix:f-getfd => 1, wire-fds => NIL. Explicitly closed the leaked test FD afterward.
Evidence execution 67b1f44c-2d9f-4917-aa16-024cfd2b076d; retained shell log 7A5450F215E480516661BC8DCB6C8F67BC2C79C1E724FB3F1BCA4C741CBD42A0.
Recommended repair: validate complete payload before popping, and establish unwind-protected local ownership immediately after pop.

* MEDIUM: X11 backend defeats cleanup-pending recovery on close failure
Location: src/display/x11.lisp:136-140.
Shared close-display correctly propagates backend failures and tracks cleanup-pending. However X11 backend-close ignores every stream close error and unconditionally discards its state. A failed stream close therefore reports successful quiescence with no retained retry handle.
Reproduction in disposable loaded X11 system: define a sb-gray:fundamental-binary-input-stream subclass whose close method signals an error. Put an instance into xclhb:make-client :stream, make-x-state :client client, and make-display :backend :x11 :backend-state state :owner sb-thread:*current-thread* :open-p T. Call public close-display.
Observed normal return, open-stream-p => T, display-cleanup-pending-p => NIL, display-backend-state => NIL.
Evidence execution f4ec82a6-b549-4c38-bf57-bfdb533ed827; retained shell log C6648E2833F6837FA74818E85002E476F073EF9C855C84C420FF4F63C2EDA1B3.
This is a distinct backend defect, not the already-fixed shared close-display defect. Test uses injected stream failure; an actual OS close failure was not induced.
Recommended repair: propagate close failure and retain backend state for retry, clearing state only after successful closure.
